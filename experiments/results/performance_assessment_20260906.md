# 全链路性能检查

## 实测范围
本机 RTX 5060 Ti 16GB，驱动 581.80，PyTorch 2.7.1+cu128 / CUDA 12.8，构建包含 sm_120。不是用户另一台 RTX 5060，不能据此判定另一台是否显存溢出或 CPU 回退。

使用第五首原曲开头准确 30 秒，新建实验输入，无覆盖原曲。GPU 运行时及 Lew/Soren 用暂存版，DSP 用当前源码。标准质量（15秒块/2秒重叠）、引导1.5、声场0.6、降噪0.2、宽度6dB、原曲参考人声方案、无风格+标准响度。计时包含子进程启动、导入、模型加载、计算和输出，不是纯 GPU kernel 时间。短片段不能线性外推整曲。

结果见 performance_20260906_201720/timing.json：

|阶段|秒|
|---|---:|
|Lew 高频重建|10.59|
|第一次 Demucs|4.00|
|低频增强|2.89|
|鼓增强|2.58|
|声场|1.89|
|原曲参考第二次 Demucs|3.99|
|人声 DSP|1.52|
|无风格母带|4.33|
|剩余解码、混合、文件操作等|2.92|
|总计|34.71|

## 确认的结构性开销
- studio_backend.py:625 与 :665：每首默认两次独立 Demucs；第二次在声场·人声阶段，未接入该阶段进度回调，可能看起来停滞。这是原曲参考方案的成本，不应直接删除而破坏效果。
- Apollo/lew_upscale.py:70–105：默认 chunk batch=1、FP32，每块 GPU 推理后同步拷回 CPU 并交叉混合。没有 autocast、torch.compile；这不等于错误，但不是为新 GPU 极致优化的路径。
- QUALITY_CHUNKS：快速20/1、标准15/2、精细10/3。长音频重叠处理倍率约1.05/1.15/1.43。精细相对标准仅按采样处理量约多24%，实际还受注意力长度、尾块补齐与启动次数影响，不能当作精确耗时比。
- 每个阶段都新启 Python，Lew 与两次 Demucs 都重新加载模型。CPU DSP 也各自承担导入开销。没有跨歌曲持久模型进程。
- Soren 是 CPU NumPy/SciPy/Numba DSP，不使用 GPU。无风格迭代响度、4倍过采样与真峰值扫描仍有成本，loud 不保证比普通风格更快。
- stage_demucs 未显式传 -d；由 Demucs 自动判断 CUDA。pipeline 的 device 参数仅明确传给 Lew，所以 --cpu 不是可靠的全链路 CPU 强制开关。

## RTX 5060 慢的待验证原因
1. 若是8GB型号，Lew FP32 + 15秒块可能面临显存压力；Windows共享显存回退可能导致极慢，但本机未采集另一台的显存数据，不能认定已发生。应同时看专用显存、共享显存、CUDA/Compute利用率，而非只看3D图。
2. 对方实际使用的 GPU Python、torch/CUDA 版本、sm_120 支持和驱动未知。安装GPU环境不代表当前进程必然使用它。CPU回退或旧运行时需由解释器路径和实际设备日志验证。
3. 两次分离与模型重载会拉长总耗时，不是GPU芯片本身速度的直接指标；需要按阶段比较。
4. 磁盘/杀毒扫描和启动导入也影响短文件与批处理，当前没有对方机器证据。

## 部署一致性问题
首次直接用暂存 runtime_gpu 的所有脚本测试，在 bass_enhance.py 因不支持 --report-json 失败。暂存 DSP 较旧，而当前后端已使用新参数。随后显式使用当前源码 DSP 完成测试，没有覆盖暂存脚本，也没有把它认定为另一台慢的根因。发布前需同步配套版本。

## 结论
本机同代16GB GPU未出现GPU阶段数量级异常：30秒输入的Lew约10.6秒，两次分离各约4秒。全链路约34.7秒，其中大量时间不是GPU计算。优先验证另一台实际运行时和显存压力，再考虑显存自适应分块、混合精度验证和持久模型进程；本次仅检查，未降低质量或改动性能算法。
